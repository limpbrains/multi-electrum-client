# Changelog

All notable changes to `multi-electrum-client` are documented here. The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/) and this project follows [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]

Pre-release. The integration suite against the Docker compose stack covers cross-impl parity, failover under toxiproxy, partial-batch retry, whole-batch limit rejection, subscription catch-up, auto-reconnect, ban detection on a strict-config Fulcrum, and pool-state connectivity. RN parity has landed: both the unit and integration suites run on-device (iOS simulator + Android emulator) in CI. No version is cut yet — `0.1.0` pending final API review.

### Added

- **Manager** (`ElectrumManager`) — single entry point for a pool of servers; transparent failover, partial-batch retry, microtask auto-batch coalescing, per-client telemetry.
- **Routing policies** — `roundRobin`, `failover`, `preferFastest`, `withSticky`. `RoutingPolicy` is a plain `(ctx) => ClientId | null` interface; custom policies are plain functions. `withSticky` moves a key's pin when the pinned client is genuinely unusable (removed, disconnected, or banned) or when a real failover retry excludes it after a failure — the pin follows the failover so later calls don't walk back into the same timeout. Hedge picks are marked `probe: true` in `PickContext` and are side-effect-free: they never create or move pins, and the built-in rotation cursors (`roundRobin`, `preferFastest` rr tie-break) don't advance on them — a discarded probe must not shift future routing. Custom stateful policies should honor `ctx.probe` the same way.
- **Typed method registry** — single source of truth for `manager.call(method, params)` overload resolution and the namespace API (`manager.scripthash.*`, `manager.transaction.*`, `manager.headers.*`, `manager.server.*`, `manager.estimateFee`).
- **Subscriptions** — handler-based `manager.scripthash.subscribe(hash, handler)` and `manager.headers.subscribe(handler)`; multi-handler dedup, disconnect-orphan / reconnect-replay with catch-up diff, fire-and-forget last-handler unsubscribe, `subscription-restored` event.
- **Cache** — caller-injected `CacheStore` with finality-gated writes for `blockchain.block.header` and `blockchain.transaction.get_merkle`. `MemoryCache` adapter ships with the package.
- **Peer discovery** — optional `discover: { enabled, onDiscover?, intervalMs? }` calls `server.peers.subscribe` on every connect; admitted ws/wss peers join the pool via `addServer`.
- **Error classifier** — pluggable; default heuristics for ElectrumX (`"excessive resource usage"`, code -101), Fulcrum (`"Subscription limit reached"`, `RPC::Code_App_LimitExceeded`), and electrs ban / rate-limit strings, plus ECONNRESET / WS abnormal-closure mapping. `composeClassifier` for caller overrides.
- **Lifecycle** — `manager.suspend({ graceMs?, cancelInFlight? })` / `resume()`; FIFO transition chain handles 3+ overlapping calls correctly. Suspended calls queue and replay (or reject with `failOnSuspend: true`). `bindAppState(manager, AppState)` wires RN's AppState to lifecycle without importing react-native.
- **Auto-reconnect** — transport-level disconnects schedule an exponential-backoff reconnect (`reconnectBackoff: { minMs, maxMs, factor, jitter }`, default `500ms→30s`, ×2, ±20%). Successful connects reset the attempt counter; `removeServer` / `stop` / `suspend` cancel pending timers; suspend / resume keeps the lifecycle path in charge of reconnect.
- **Pool-state events** — aggregate connectivity for UIs: `manager.on('pool-state', ...)` emits `{ status: 'online' | 'degraded' | 'offline', usable, connected, total }` whenever the aggregate status changes, including a ban expiring (an internal timer armed for the earliest `bannedUntil`, capped below the `setTimeout` clamp, fires the recovery without any traffic). Exactly one baseline event after `await start()` — even when every initial connect failed — and one after `resume()`; suppressed across suspend (a deliberate pause is not an outage). Clients mid-`removeServer` are excluded from the computation, so intentional removal of a healthy server emits nothing while an unrelated outage in that window still emits immediately. `manager.poolState` getter returns the same snapshot on demand.
- **`ensureConnected()`** — BlueWallet-style guard for "must be live" call sites (`await manager.ensureConnected(); await manager.transaction.broadcast(raw)`). Waits (default 30 s budget) for the reconnect loop to produce a usable server, then verifies liveness per the probe policy: `'auto'` (default) sends a wire `server.ping` through the normal routing pipeline only when no usable client has answered within `probeStaleMs` (10 s) — the wire probe catches half-open sockets (established but dead — the mobile-NAT shape) that connection state cannot see, and a dead pick times out and retries on another server with telemetry updated along the way. Typed throws (`SuspendedError` / `NoClientAvailableError` / last real ping failure / abort reason); the wall budget and abort signal cover the whole call, including a `resumeIfSuspended` resume and the probe itself. Each concurrent caller keeps its own budget/signal — only the liveness ping is single-flight — and `stop()`/`suspend()` interrupt every phase of the wait immediately (parked waiters, resume race, probe race, retry cooldown) instead of letting callers sit out their budget.
- **Transports** — `WsTransport` (universal: Node 22+, browser, RN, Bun), `TcpTransport` (`node:net`), `TlsTransport` (`node:tls`, awaits `secureConnect`). Shared `LineFramer` for all three. Transport registry lets the package ship a separate browser entry that registers only ws/wss.
- **Conditional package exports** — root `.` resolves to `index.browser.js` for browser bundlers (no `node:net` / `node:tls`), `index.js` for Node / RN / Bun.
- **Examples** — `examples/{node,bun,browser,rn}-basic.*`.
- **On-device React Native test runs** — the complete node unit suite AND the docker-backed integration suite run unmodified inside a real React Native runtime (Hermes) on iOS simulators and Android emulators via `react-native-harness`. A Metro alias maps `vitest` to a thin shim (`test/rn/app/harness/vitest-shim.ts`) — harness's `expect` is `@vitest/expect` and its mocks are `@vitest/spy`, so only fake timers (`@sinonjs/fake-timers`) and `describe.each` needed filling. `node:net` / `node:tls` resolve to `react-native-tcp-socket` through the exact alias the README documents for RN consumers, so the tcp/tls transport tests exercise the real native socket module on-device. The two `ws`-server-backed files run against `test/rn/app/harness/ws-shim.ts`, a minimal RFC 6455 WebSocket server implemented on react-native-tcp-socket — the ws server runs on the device itself. The integration suite reaches the host's docker stack from the device (iOS simulator via `127.0.0.1`, Android emulator via `10.0.2.2`); toxiproxy/bitcoind admin helpers are fetch-based and work as-is. Scripts: `test:rn`, `test:rn:setup`, `test:rn:ios`, `test:rn:android`, `test:rn:integration:ios`, `test:rn:integration:android`; CI jobs `rn-ios` (unit) / `rn-android` (unit + integration against the compose stack).

- **Hedged requests** (opt-in) — `ManagerOptions.hedging: { afterMs }` arms a timer on every eligible call, on the direct path AND on the auto-batch path (where the whole coalesced wire batch is hedged at the group level, so coalescing survives); if the picked server hasn't answered within `afterMs`, the same request (or wire batch) fires on a second policy-picked server without cancelling the first, and the first real answer settles the caller(s) (the loser's late reply is swallowed but still recorded in telemetry, so the slow server's stats stay honest). Bounds the "server accepts TCP then hangs" stall to `afterMs` instead of the full `requestTimeoutMs` — the live bench's S2b scenario paid the whole 10s timeout while three healthy servers sat idle. Only an explicit allowlist of known-idempotent reads hedges by default (the typed registry minus broadcast / subscribe, plus `server.features`, `blockchain.scripthash.get_mempool`, `blockchain.relayfee`); unknown/vendor methods hedge only with a per-call `CallOpts.hedge: true` (caller asserts idempotency), while `blockchain.transaction.broadcast`, `server.version` (session negotiation — a duplicate is rejected by ElectrumX and another server's answer doesn't describe this session), and `*.subscribe` / `*.unsubscribe` are hard-excluded regardless of any override. A batch group hedges only when every item in it is eligible and has attempt budget for a second dispatch (`retry: 'none'` never hedges); mixed groups are dispatched unhedged. The batch hedge's second server is routed per item (the same pass as the flush and retry re-picks) and the hedge fires only when every item's pick agrees on one client — diverging picks, which only arise under request-dependent policies such as `withSticky`, skip the hedge and wait out the primary rather than splitting the wire batch. When one branch answers with a mixed results array (some successes, some retryable failures), the successes settle immediately but the retryably-failed items wait for the sibling dispatch instead of retrying at once: a late sibling success resolves them, a sibling non-retryable error rejects them, and anything else retries with both servers in the item's excluded set and the attempt budget advanced by both dispatches — an item can never race a duplicate onto the very server being hedged around or exceed its dispatch budget. If both branches fail at batch level, the retry loop continues with both clients excluded, the attempt budget advanced by both tries, and each item seeded with its own per-item error whenever the failure carried one (a whole-batch transport cut legitimately shares one cause).

### Changed

- **Batch retries are re-batched** — retryable survivors of a failed wire batch (transport cut, timeouts, rate-limit, Fulcrum's whole-batch `id: null` rejection) now re-route as wire batches per policy re-pick instead of degrading to per-item single calls. Measured on the live bench (S2, real-history wallet): a ~334-item batch dying mid-flight previously turned into ~600 sequential single-call retries — 69s wall for a sync that takes ~7s healthy; the group retry costs one extra round-trip per fallback server. The retry re-pick is made per item (same pass as the initial flush), then items are regrouped by picked client — so under `withSticky` (or any request-dependent policy) items with different sticky keys land on their own sticky-consistent targets instead of following a representative item; in the common case all survivors still travel as one batch. Per-item semantics are unchanged: non-retryable items still reject immediately, each item keeps its own attempt budget and exclusion set, and a lone survivor takes the single-call path (which also carries hedging).

### Security

- **A throwing consumer listener can no longer strand a transport.** Terminal teardown (retire, unpublish, destroy) now completes *before* any listener runs, and transport `emit` isolates listener exceptions the way the manager's already does. Previously an `error` listener that threw skipped the cleanup that followed it, leaving a retired-but-still-published socket: every native event was stale, so nothing could finish the teardown, and `connect()` refused to replace it — an unreconnectable transport plus a leaked socket.
- **A framing-limit teardown retires its socket.** Hitting `maxLineLength` emitted the terminal error/close pair but left the generation current, so anything the same socket had queued behind it — more bytes, another overflow, its own close — still surfaced after the connection was declared dead.
- **A dying socket can no longer be handed back as a live connection.** If the peer closed between the ready/open event and the continuation that publishes the socket, `connect()` used to resolve successfully over a dead socket (and, on WebSocket, emit a close for a connection the caller was never given) — leaving a published-but-dead socket that also blocked reconnect. Such an attempt now fails, publishes nothing, and emits nothing; a close before `open` fails the attempt immediately instead of waiting out the connect timeout. A *published* peer close retires its generation, so no later data or error from that socket can surface either.
- **The connect-abort hook is generation-scoped.** It was a single shared slot that any candidate could clear: a delayed event from a retired candidate wiped the live candidate's hook, so `close()` had nothing to abort and sat out the full connect timeout (~10s by default) instead of its 500ms teardown bound.
- **Transport connect / close are serialized by an explicit lifecycle gate** (`src/transport/lifecycle.ts`, shared by both transports). Flags plus a generation counter left overlap windows that each looked like a separate bug: a `close()` landing between the ready event and the publication of the socket could return while the connection went live behind it; an immediate reconnect could hit a not-yet-cleared "connecting" flag; a slow teardown could retire the connection that replaced it; two concurrent closes could each retire a generation; and a failed or timed-out attempt stayed the current generation, so its handlers could still emit after `connect()` rejected. The gate now owns the ordering: close retires the active generation first, aborts an in-flight connect and awaits its settlement, and concurrent closes share one operation; a failed attempt retires itself and destroys its candidate socket.
- **One live socket per transport, enforced.** `connect()` now rejects while another connect is in flight or a socket is already open (matching `ElectrumClient`'s own guard) instead of silently replacing the live socket. Previously a direct consumer of the exported transports could leave the instance write-only — a second `connect()` retired the first socket's handlers, so if the replacement then failed, `send()` kept writing to a socket whose reads and terminal events were ignored; concurrent attempts could also publish the loser over the winner. `close()` now retires the generation too, so nothing from an abandoned socket (notably the WebSocket backstop path, where browsers expose no `terminate()`) can surface after `await close()` resolves.
- **Socket generations are isolated.** Both transports now stamp every connect attempt with a generation and give it its own `LineFramer`; every data / message / error / close handler goes inert once a newer attempt supersedes it. Previously a delayed event from a torn-down socket could append to (or reset) the *current* connection's partial line, deliver a stale frame as if it came from the live socket, trip the line cap and disconnect a healthy connection, or — after a close backstop left `this.ws` null — emit a terminal close for a replacement that was still connecting.
- **Transport connect races closed.** A framing overflow delivered between the ready/open event and the connect continuation used to be undone by that continuation: it reassigned the destroyed socket and resolved `connect()` successfully, so the caller held a "live" transport over a dead socket and `send()` wrote into the void. Each attempt now carries its own terminal state and `connect()` rejects instead of reviving it. Close handling is likewise scoped to a socket generation — a delayed native close from a torn-down socket can no longer fire a terminal event describing the *current* connection (relevant for direct consumers of the exported transports, which can reconnect immediately).
- **Bounded line framing** — a malicious or broken server could stream newline-free data and grow the shared `LineFramer` buffer until the process (or browser tab / RN app) ran out of memory. Every transport now caps one logical line and the retained partial buffer (`maxLineLength`, default 4 MiB); on overflow the transport emits an `error` plus `close` event and tears the connection down, so in-flight requests fail over immediately instead of waiting out their timeouts.
- **Pinned the integration ElectrumX image by digest** — `lukechilds/electrumx:latest` is mutable; CI now tests against an immutable `@sha256` reference.
- **A README "Security notes" section** documents the peer-discovery, broadcast-retry, hedging-privacy, and TLS-verification tradeoffs.

### Fixed

- **Live pushes are never deduplicated.** The registry suppressed a push whose status equaled the stored baseline — but the protocol says a client MAY be notified without a status change and MUST be notified on a same-height reorg, where the blockhash changes and the status hash does not. The suppression swallowed exactly that mandated notification, leaving a consumer on a merkle proof tied to the orphaned block with nothing to correct it. Every live push from the bound server now reaches handlers (a duplicate costs one refetch under the resync contract); equality suppression remains only on synthetic paths — attach replay, rebind responses and flushes, which are our replays, not server notifications.
- **The unsubscribe chain tags the session it actually dispatches on.** The session seq guarding the poison decision was captured before awaiting a prior unsubscribe for the same key; a client recycling during that wait made the chained call dispatch on the NEW session while carrying the old seq, so an ambiguous failure skipped the poison and reopened the late-unsubscribe hazard. The seq is now captured at entry and re-checked after the prior settles, immediately before dispatch: a session that died or recycled during the wait has nothing left to clean (its subscription died with it), so the chain skips instead of writing a spurious unsubscribe to a fresh session whose ambiguous timeout would poison — and later retire — a healthy socket.

- **Discovery probes respect bans.** The peer-discovery probe is strictly addressed (its results must be attributed to the probed peer), but strict addressing had silently become permission to bypass a rate-limit ban — the re-poll timer would probe a peer during the very cooldown that peer's throttling earned, prolonging it. Strict pins are now ban-aware at the routing layer itself, with an explicit `pinBanExempt` opt-in used only by the registry's wire unsubscribe (cleanup of state the session already holds) — a future strict-pin caller cannot silently inherit ban-bypass. A probe refused during a cooldown still re-arms the discovery poll timer, so one unlucky poll cannot silently end discovery for the life of the socket. The scripthash `subscribe` docs and README also now state the status-payload contract explicitly (a change signal to resync on, not an authoritative digest to persist) and the library's trust model (a non-SPV client trusts the serving peer's chain view; SPV is out of scope).

- **`preferClient` keeps its documented public semantics.** Making `retry: 'none'` escalate the hint into a strict, ban-bypassing pin silently changed a public option's contract — a caller preferring a banned server would be routed to it over a healthy peer. The strict addressed-call behavior now lives in its own `pinStrict` option, used by the registry's wire unsubscribes and discovery's peer probes; `preferClient` alone is a hint with the documented fallback, whatever the retry policy.

- **Poison follows the session, not the client id.** On socket loss the client rejects in-flight calls and then publishes `disconnected`; the unsubscribe's rejection handler runs as a later microtask — after the disconnect already cleared the key's poison — and re-poisoned the DEAD session's client id, retiring the fresh session that next reconnected under it (in a single-server pool, failing the replacement subscribe outright). An ambiguous failure now poisons only when the session seq captured before the call still matches at settlement (and the client is connected): the counter bumps on every `connected` transition, so a replacement session — even one connected synchronously before the multi-hop rejection settled — can never be mistaken for the session the unsubscribe was written to.

- **Storage authority follows the serving socket for scripthash statuses too.** Foreign buffered statuses remain change-signal deliveries (a consumer resyncs on every callback), but they now fan out WITHOUT passing through storage: the record's `lastKnownStatus` — which feeds every joiner's replay, including one attached re-entrantly from inside the fan-out itself, and the dedup baseline — only ever holds what the serving socket reported. Handlers still awaiting their first status sit the fan-out out (they were promised a status from a live binding), a rebind that flushed a foreign change signal reports `drift: true` even when the serving values compare equal, and the uncertain-baseline rule still lets the serving server confirm its own equal status once, so a mempool rollback is never deduplicated away.

- **An ambiguous unsubscribe poisons its session; the retire is deferred to the hazard.** A wire unsubscribe that times out (or dies in transport) was written to the session and may still execute later — after a replacement subscribe on that same session, silently cancelling it; the settlement barrier alone cannot close this, because a timeout is not proof of non-execution. Electrum subscriptions are session-scoped, so retiring the socket kills the stray unsubscribe with its session — but retiring eagerly would cycle a merely-slow server's whole connection on every unsubscribe, hazard or not. The registry instead marks the session poisoned for that key and retires it only when a replacement subscribe for the key actually appears; a wallet that never re-subscribes triggers no retire at all, and a disconnect clears the poison (the stray unsubscribe died with its session). A settled response — success or RPC error — proves execution and never poisons; neither does a pin that found no connection or a pre-dispatch `SuspendedError` (nothing was written, and force-closing a socket mid-grace-drain would fail the very in-flight requests `suspend()` promised to finish).
- **Native WebSocket framing is strict: the message is the unit.** In `'message'` mode a text payload was still run through the newline framer, so a message packing several newline-separated payloads was silently split — and the length cap was unbounded in aggregate: one enormous message of millions of tiny newline-joined lines passed every per-line check while the runtime held the whole message. The Electrum protocol puts exactly one JSON-RPC payload per WebSocket message; message mode now takes the payload whole. The RAW message is bounded by the cap plus a 16-char padding allowance before anything else (pre-decode via the minimum-decode heuristic for binary, re-checked exactly on the decoded length — mostly-ASCII binary decodes 1:1, so without the second check a flood up to 3× the bound slipped through; an unbounded padding run is itself a size violation, not an exemption). Small terminator runs at either edge strip as padding — `'{...}\n\n'` and coalesced CRLF-CRLF keepalives are one payload or none — and the bounded payload is emitted WHOLE, interior newlines included: RFC 8259 permits LF as insignificant whitespace, so a pretty-printed response is valid, and several newline-separated roots fail loudly at the client's JSON decoder as one malformed value. Byte tunnels (`'newline'` framing) keep the framer path, with a per-server aggregate message bound: `maxMessageLength`, defaulting to four full-cap lines with their terminators, floored at 8 MiB (~128 MiB at the default line cap; must be at least `maxLineLength + 1`, validated at construction, and rejections name the bound actually violated) — sized so legitimate coalescing (RFC 6455 ties messages to no size; a bridge may legally pack several near-cap responses into one message) clears it, while a flood of tiny lines in one enormous message still fails — native browser WebSocket exposes no `maxPayload`, so this bound cannot be delegated to the platform there.
- **A failed tip install can no longer strand the cache for the session.** The internal headers-subscription install was guarded by a boolean: a `connected` trigger landing while the first attempt awaited its response was discarded, so if that attempt then failed non-retryably, the dropped trigger had been the only retry — a stable session ran with no tip and every cache write silently disabled. Install is now an awaitable single-flight task; a trigger joining mid-flight queues exactly one retry, consumed only if the current attempt fails. The task reference is reset synchronously with the loop's exit, so there is no microtask window in which a trigger can join an already-dead task and lose its retry.

- **A replacement subscribe is serialized behind the prior unsubscribe.** Unsubscribing the last handler sends the wire unsubscribe fire-and-forget, so an immediate re-subscribe for the same key could reach the server while the unsubscribe was still in flight — and Electrum servers may process a session's requests concurrently (ElectrumX `INITIAL_CONCURRENT`), so the late unsubscribe could execute after the new subscribe and silently cancel its live subscription. A replacement subscribe now waits for the pending unsubscribe to settle (a settled response being the only proof the server executed it) — bounded by the request timeout, epoch-checked so a registry teardown during the wait cannot leak a stray wire subscribe, and released by `clear()` so a fresh registry never parks on the old epoch's call. Pushes received while parked predate the wire call and are purged with the rest of the pre-call buffer.
- **An oversized WebSocket message fails before the decode allocation.** The WebSocket API materializes each complete message before firing `message`, so no client-side cap can bound that first allocation — but the UTF-8 decode made a second full copy before the framer's length check ran. The pre-decode gate is mode-aware: in message mode the whole payload (edge terminators stripped) is the unit the cap bounds, so a trailing `0x0a` byte cannot buy a hostile peer the decode allocation; in newline mode a payload carrying no newline byte — one line by construction, `0x0a` is unambiguous in UTF-8 — is judged the same way, and multi-line payloads keep the per-line path, and the docs state the cap's real guarantee (framer retention, not platform receive; use the WebSocket implementation's own `maxPayload` for a pre-delivery bound).

- **A foreign pooled server can no longer inject subscription payloads.** When a push raced a subscribe/rebind, the registry delivered every buffered status — including ones from servers other than the one that answered. For scripthash statuses that is harmless-by-design (the status is an opaque change signal; consumers resync from a server they trust), but a header's payload IS the data: the manager's finality gate consumes its `height` directly, so one bad pooled server pushing an inflated tip during any subscribe race could mark unfinalized data as final and poison the cache indefinitely. Electrum subscriptions are connection-scoped — an unrelated socket has no authority over a binding's view. Foreign buffered payloads are now delivered only for opaque-status methods; for everything else the flush is a pure purge — even the answering server's own buffered header is dropped, because its order against the response is unknowable (a push coalesced into the response's chunk buffers too) and replaying a stale header would REGRESS the tip the finality gate reads, while dropping a newer one merely waits for the next block. Never-regress wins — and the SIGNAL survives the purge: a differing dropped status marks the baseline uncertain, so the rebind still reports `drift: true` and one equal follow-up push is not deduplicated. (A subscribe attempt that timed out after the server installed the subscription is the accepted bounded-leak class, now documented at the call site: it pushes into the void until that connection recycles.)

- **Default line cap admits the protocol's largest valid response.** The framer's default `maxLineLength` was 4 MiB — below the Electrum protocol's own envelope: a consensus-valid 4M-weight-unit transaction returns from `blockchain.transaction.get` as ~8 MB of hex (ElectrumX ships `MAX_SEND = 8,100,000` precisely so it can be served; 10,000,000 on AuxPoW chains), and the VERBOSE form is bigger still — the daemon's JSON carries the serialized transaction in `hex` and the witness a second time in `vin[].txinwitness`, approaching ~17 MB for a witness-heavy transaction — and a BASE-heavy transaction is worse: `scriptPubKey.asm` renders each opcode byte as a mnemonic up to ~23 chars, so ~1 MB of consensus-valid script becomes ~23 MB of asm, pushing the verbose envelope to ~28 MB. Such a response tripped the cap, tore the connection down, and — since every retry returns the same data — failed deterministically forever. The default is now 32 MiB; the cap is also finally reachable from the manager: `ServerSpec.maxLineLength` / `Endpoint.maxLineLength` size it per server, the manager's `maxLineLength` option sets a pool-wide default that also covers discovery-admitted peers (which no per-spec value can reach), and the per-server declaration takes precedence over a cap passed at transport construction — the construction value is a fleet default, so the other precedence would silently disable the per-server knob for every custom-factory deployment. This deliberately raises the per-connection memory bound 8× over the original — the floor for a correct default is the protocol's own envelope; memory-constrained deployments that never fetch large transactions should pass a lower value.
- **A routing ban no longer silences a live subscription.** The registry's `isClientConnected` was wired to the ban-aware routing predicate, so a server banned (e.g. by a concurrent rate-limit error) while its subscribe response was in flight produced an orphaned record even though the socket was up and the server had accepted the subscription: the initial status was withheld and every push only buffered — in a single-server pool, silence for the whole ban, renewable by repeated throttling. Ownership now follows the socket (`connected` state only); bans keep gating routing of new calls, which is all they ever meant. The wire unsubscribe is now strictly pinned for the same reason: `preferClient` with `retry: 'none'` goes to that exact connection or fails — previously a banned pin fell through to `policy.pick`, sending the unsubscribe to a server that never held the subscription, where it could land after a fresh re-subscribe and silently kill it.

- **Native Electrum-over-WebSocket servers work.** The protocol sends one complete JSON-RPC payload per WebSocket message with no trailing newline (Fulcrum's `ws=` mode, public WS gateways); requiring the delimiter held every response in the framer forever, so each request timed out against every compliant native server — and the outbound side appended a newline a strict per-message parser may reject. Framing is now a per-endpoint declaration, `wsFraming: 'message' | 'newline'` (default `'message'`, the protocol's own definition): in message mode the boundary *is* the delimiter — injected through the framer so CR handling, the length cap and keepalive filtering apply through the one code path — sends are bare, and a binary message ending mid-character fails loudly instead of leaking a truncated payload plus a corrupted successor. `'newline'` declares a byte tunnel relaying a newline-delimited TCP stream (this repo's demo bridge does); the two cannot be told apart from traffic — a tunnel's fragment looks exactly like a native server's complete message — so it is declared, not guessed. No test at any level previously reached a native-WS server; tracked as the integration-coverage gap in #28.

- **An uncertain baseline no longer deduplicates a repeated status.** Scripthash statuses repeat without any reorg — a mempool transaction dropped by RBF, expiry or conflict restores the exact prior history — so a status left behind by an unorderable flushed push could swallow the genuine later push of that same value, and the consumer stayed on the other candidate indefinitely. The record now marks its baseline uncertain after such a flush: one equal push (or rebind answer) goes through, delivered as drift, and the ambiguity is resolved by that very delivery.

- **The subscription registry was restructured around one model instead of five patches.** A status is an opaque *change signal* — consumers resync on every callback, they do not interpret the value — so a push that cannot be ordered against a subscribe/rebind response is simply delivered after it, in wire order: whichever was really newer, the consumer's final resync fetches the server's current truth. This replaces the wire-refetch tie-break and with it the per-record `revision`, the binding generation, the `reconciled` flag threading and the deferred restore announcements — a subsystem that had produced more defects than the ambiguity it resolved (a failed refetch dropped the change entirely; its answer could overwrite a newer live push or land while the record was unbound; the deferred announcement fired for bindings that were gone or duplicated). Buffered pushes from *other* servers are now delivered too, not discarded — a change signal from any pooled server is worth one resync, and dropping one could hide a transaction behind a lagging rebind answer.
- **Cleanup of a stale rebind's leaked subscription is deliberately conservative.** The previous deferred re-evaluation acted on a snapshot the next transition could invalidate — it was observed unsubscribing the very server a successor had just rebound to, silently killing a live subscription. The unsubscribe is now sent only when nobody could own it: a leaked subscription pushes into the void until its connection closes, which is bounded and self-healing; a wrong unsubscribe means missed transactions with nothing to correct them.
- **Suspend options are frozen at submission.** `suspend()` snapshots and validates `graceMs` once, before publishing teardown intent, and the queued transition consumes only that snapshot — so a caller mutating its options object after submission can no longer wedge the manager in `resuming`, and an invalid `graceMs` now rejects uniformly in every lifecycle state.

- **Work that spans a wire round-trip is tied to the binding that started it.** The tie-break refetch and the restore announcement deferred behind it both outlive the check that authorised them, so a disconnect in between announced a recovery nothing was delivering, a reconnect of the *same* server announced it twice (the second with a pre-rebind baseline, reporting drift where the first reported none), and a late answer from the departed server was still handed to handlers — overwriting the status of whichever binding had replaced it. Each record now carries a binding generation: a name comes back on reconnect, an identity does not. A ban is deliberately not a change of binding — the record stays bound and the server keeps pushing — so it still announces.

- **Framing a fragmented line is linear again.** Sealing retained pieces by appending to a growing 64 KiB string copied that whole block on every chunk, because strings are immutable: a 4 MiB line delivered one byte at a time — fragmentation the peer chooses — blocked the event loop for **6.6 seconds**. Fragments are collected and joined once per block instead: the same line costs ~130 ms, and retention still follows the line rather than the chunk count.
- **An unorderable push no longer rolls the status backwards.** When the tie-break cannot be asked because the answering server is gone, the response stands and the ambiguity waits for the rebind that a disconnect guarantees — replaying a push that may *predate* the response would pin the record to a status no later push corrects. When that server is merely banned the record is still bound to it, so its push is delivered: nothing would rebind that record, and its next push moves the status forward anyway.
- **A tie-break answer cannot overwrite a newer notification.** The refetch describes the subscription as of when it was asked; a live push arriving first now wins, and the answer is discarded rather than moving the record — and its drift baseline — backwards.
- **`subscription-restored` reports drift after reconciliation.** It was announced with drift computed before the tie-break finished, so a consumer using it to decide whether to refetch history got "nothing changed" and then a changed status. The announcement now waits for the reconciliation — without blocking the rebind itself, which would hold the record in its single-flight slot across a round-trip and make a concurrent recovery skip it.
- **A handler removed and re-added is a new registration.** Identity was the function reference alone, so a fan-out snapshot taken before the swap called the replacement again, and the spent unsubscribe handle tore it down. Registrations carry a token.
- **A server added while a teardown is pending is not dialled** — and is scheduled for reconnect, so it still comes up if that suspend never happens (a rejected `graceMs` leaves the manager running). Discovery likewise refuses probes and `onDiscover` results while an intent is pending, by asking rather than by cancelling — a cancel would not come back if the intent were rejected.

- **A handler that stops listening mid-delivery is not called again.** Fan-out iterates a snapshot so a callback can safely add or remove handlers — but that protects the loop, not the callers: a handler unsubscribed by an earlier callback in the same push still received it, as did every handler once a callback tore the registry down (`clear()` empties the subscription map while handler sets stay populated, and by then every unsubscribe handle is a no-op). Both are now checked once, where handlers are actually invoked, so all four fan-out paths follow the same rule.

- **A subscriber never receives a stale snapshot as its "current" status.** Joining a key another caller already watches attached immediately and replayed `lastKnownStatus` — whatever its age. Whether that value was current depended on whether the record happened to be bound: suspended, offline or mid-rebind, the joiner was handed an hours-old status while subscribing to a *new* key at the same instant threw. A handler that joins an unbound record now waits, and receives the status from the first binding that holds, even if it never changed.
- **The tip subscription is retried when a server connects.** It was attempted once from `start()` / `resume()` and its failure only surfaced as an `error` event, so a cache-configured manager started while nothing was reachable ran the whole session with an unknown tip — and since finality cannot be proven without one, its cache was never written again.

- **A status pushed while a subscribe was in flight is no longer guessed at.** The buffer proves only that a push arrived *during* the call — not that it followed the response. A server that already holds the subscription on that socket (a rebind onto a live connection) pushes a change and only then answers, and both land in one synchronously dispatched chunk, so nothing distinguishes them. Replaying the push regardless pinned the record to a status no later push would correct. The registry now asks: it re-issues the subscribe pinned to the server that answered and delivers *that*, falling back to the buffered push only when that server is gone.
- **The subscription a server actually holds is the one we cancel.** A record can be orphaned while the server that answered its subscribe is still connected and pushing (it was banned when we tried to bind). The last-handler unsubscribe told only the bound client — nobody — leaving that subscription running with no consumer for the life of the connection; and a stale rebind's cleanup, which decides ownership from the successor's binding alone, could unsubscribe a successor that had answered on that same server. Both now follow `servedBy`.
- **A restore is not announced for a subscription the caller just dropped.** `subscription-restored` was emitted after handlers had run synchronously, so a handler that unsubscribed inside its own callback still produced the event — sending a consumer off to refetch history for an address it no longer watches.

- **A rebind that lands on a server which stopped being usable no longer reports a restore.** If the answering client disconnected — or merely got banned, which keeps its socket connected — between returning the status and our continuation resuming, the record stayed orphaned while `subscription-restored` was emitted anyway, telling consumers the subscription was live when nothing was pushing to it. The status itself is still delivered (it is real data from the server that answered); only the announcement waits for a bind that actually holds. And a **ban expiring now retries orphaned subscriptions** — it is the one recovery that fires no socket event, so on a single-server pool such a subscription used to stay silent indefinitely.

- **A protocol failure before the connection opens fails the attempt.** An unusable frame (oversized line, undecodable bytes) arriving before `open` / the ready event muted the native close and then had nothing left to settle `connect()` — the caller waited out the whole connect timeout on a socket the transport had already destroyed, while the client had gone `disconnected` and the manager's reconnect hit `connect already in progress`. Both transports now fail the attempt instead, and emit nothing for a socket `connect()` never handed out (the rejection is the report; a *published* connection still gets `error` + `close` so its in-flight requests fail over at once). A pre-open connect error also retires and tears the socket down before rejecting, so a queued frame delivered in the same turn cannot surface as data from a connection that never opened.

- **A routing policy cannot outrun teardown.** `policy.pick` is user code and runs after the caller's teardown check, so a policy that suspends the manager from inside `pick()` still had its own request put on the wire. The check now sits immediately after the routing decision — in `pickFor` for the single and hedged routes, in the batch routing loop for auto-batch — where every dispatch path resolves its target.

- **Every wire dispatch respects teardown, not just retries.** A call that passed the entry check and then waited (on a cache read, on a rebind continuation) could still send its *first* request after `stop()`; group hedges and re-batched retries started new batches during the suspend grace; and a disconnect caused *by* the teardown triggered a subscription rebind onto a peer that was next in line to be closed. All of those paths now check teardown intent, which includes a suspend that has been submitted but whose transition has not run yet.
- **`start()` stops when a `stop()` overtakes it.** It is not part of the serialized transition chain, so a stop landing during the initial connect wave left it to publish a pool baseline and subscribe for the tip on a manager that had already been torn down.
- **A suspend queued behind a resume is honoured.** `resume()` checked only for a stop after its awaits, so it would re-install the tip subscription, flip to running and drain queued calls onto clients the very next transition was about to disconnect.
- **Discovery stops at suspend intent** rather than after the grace drain, so a probe timer cannot fire — or an `onDiscover` resolve — while the manager is already suspending.
- **A retained line is held in blocks, not one piece per network chunk.** The peer chooses how it fragments the stream: a 4 MiB line delivered byte-by-byte became 4 million strings (~34 MiB heap, ~70 MiB RSS) even though the line was inside the cap. Small pieces are merged into a bounded block, so the piece count follows the line length instead of the chunk count.
- **A listener that closes the transport stops the rest of the chunk.** Lines are emitted as they are framed, so `close()` from the first line of a multi-line chunk used to be followed by the remaining lines — from a socket the caller had already retired.
- **Event fan-out iterates a snapshot** in the manager and both transports. A `Set` iterator revisits an entry removed and re-added while it runs, so a listener that unsubscribed and resubscribed itself from inside its own callback was called again, and again.

- **A coalesced subscriber cannot attach after `clear()` either.** Two callers subscribing the same key share one wire call; only the caller that issued it re-checked the registry after the response. The joiner attached to a record teardown had already dropped — its handler ran after shutdown and it received an unsubscribe handle owning nothing — reachable whenever the first subscriber's handler stops the manager from inside its own replay.

- **A newline-free response no longer costs quadratic work.** The retained partial line was one growing string, and appending to it built a rope that every delimiter scan then flattened — a server dripping 4 MiB in 256-byte pieces blocked the event loop for ~4.6 seconds (measured) before the length cap could trip, without ever exceeding it. The framer now keeps the pieces as it received them, scans each chunk once, and joins only to emit a finished line: the same drip costs ~2 ms. An over-long line is also rejected before it is materialized.

- **A frame full of short lines no longer multiplies into memory.** Complete lines were collected into an array before any of them reached a listener, so one WebSocket frame of `"x\n"` repeated held a string per line at once — measured at ~13x the frame's own size (4 MB in, 54 MB of heap), which turns a frame the peer chooses the size of into an out-of-memory kill even though every line is far below `maxLineLength`. Transports now consume lines as the framer finds them.

- **Teardown stops new wire work.** An already-dispatched request may finish during the suspend grace, but a *new* retry, hedge or connect-time handshake started after `suspend()`/`stop()` was requested went out on a socket teardown was closing — and one such retry could even answer a caller successfully after `stop()` had returned. Those dispatch sites now check teardown intent, and `stop()` invalidates discovery and the subscription registry *before* awaiting the transition it is stopping.
- **`suspend({ graceMs })` validates its budget and yields to `stop()`.** `Infinity` parked the drain loop with a queued `resume()` stuck behind it, and `stop()` waits on that transition — the manager could never be torn down; `NaN` and negatives were the opposite failure, making every deadline comparison false so the drain the caller asked for was silently skipped. Both are rejected now, checked at the top of the transition on the value it actually uses (after the `?? 2000` default, so `null` still means "unset") and before any state changes — an argument error must not leave the manager stranded in `suspending`. A `stop()` arriving mid-grace also ends the drain immediately.
- **A subscribe resolving between record install and handler attach is no longer honoured after `clear()`.** The epoch check inside the registry task did not cover the gap before `subscribe()`'s own continuation resumed: the caller got a handler call and a live unsubscribe handle for a registry that had been torn down.
- **Stale rebind cleanup cannot silence a live subscription.** Electrum keys a subscription by method+params on a connection, so the compensating unsubscribe sent for a replaced record could cancel the *successor's* subscription on that same server. It is now skipped when a successor holds — or is currently establishing — that server's subscription.
- **A notification from another client cannot erase the serving client's buffered status.** Early notifications are buffered per (key, client); one slot per key let unrelated traffic overwrite the status that was about to be delivered, and the flush then dropped both.
- **An unsubscribe handle only affects the registration it came from.** Handles captured key and handler, so a stale handle could remove a handler from — and tear down — the record that replaced it, including sending a wire unsubscribe for a live subscription.
- **Re-subscribing the same handler from inside its own callback is idempotent.** `attach` replayed the status even when the handler was already registered, so a handler that resubscribed itself was re-entered on every replay — unbounded recursion.
- **A reconnect ends a rebind backoff instead of waiting it out.** A sleeping retry (up to 10s at later stages) kept the subscription dead across a reconnect that could have restored it immediately; `restoreOrphans` now wakes sleepers and the delay ladder restarts.
- **`cancelFor()` cancels an in-flight discovery probe.** It cleared only the timer, so a probe whose source client had disconnected could still admit peers via `onDiscover`.

- **A queued auto-batch no longer reaches the wire after `stop()`.** `call()` only enqueues; the flush runs a microtask later, by which time `stop()` had marked the manager stopped and yielded — the flush then dispatched onto a socket teardown was closing, and the caller saw a transport error instead of being told the manager was gone. A flush that finds the manager not running rejects its items with `SuspendedError`.
- **A peer approved after `suspend()` is not admitted.** The post-`onDiscover` guard asked only whether the manager was *stopped*, which is false while suspended, so a slow callback resolving after `await suspend()` returned added a server to a pool that was supposed to be quiescent — and `resume()` connected it. Discovery runs now carry a generation that `cancelAll()` invalidates.

- **A replacement subscription is no longer stranded by its predecessor's rebind.** Rebind single-flight was keyed by canonical key alone, so a new record at a key whose previous record still had a rebind in flight was handed that task — which exits on its identity check and recovers nothing. The replacement then sat orphaned, receiving no notifications, until some unrelated client transition happened to run recovery again. Pending rebinds are now owned by a record, not a key.

- **A decoded string chunk cannot jump ahead of a half-received character on TCP.** A socket shim that emits both strings and bytes could interrupt a UTF-8 sequence with an already-decoded string; appending it placed it *before* the character whose bytes arrived first, turning a malformed stream into valid-looking, reordered JSON. TCP now ends the connection there, as WebSocket already did for a text frame interrupting a binary one.

- **`stop()` no longer returns with a rebind still sleeping.** The retry backoff used a plain `setTimeout`, so after `clear()` the task stayed alive and its timer kept the event loop referenced for up to 10 seconds — a script that stopped the manager did not exit. Backoff sleeps are unreferenced and cancelled by `clear()`.
- **Unsubscribing during a rebind no longer leaks the wire subscription.** The record was orphaned when its last handler left, so the unsubscribe had no server to go to; the rebind then succeeded and created a live subscription on the replacement that nothing would ever cancel — the server kept pushing for a subscription with no consumer. A rebind that finds its record gone now sends the unsubscribe to the server that answered it.
- **A connect timeout cannot deliver data.** Both transports rejected and destroyed the socket without retiring the attempt first, so a socket flushing buffered bytes on the way down (an injected / React Native one, synchronously inside `destroy()`) surfaced them as data from a connection the caller was being told had timed out.

- **`stop()` can no longer be undone by a subscribe that was in flight.** Its continuation was already queued when `clear()` ran, so it re-installed a record and called the handler on a shut-down manager. The registry now carries an epoch: a wire call that outlives the registry it started in fails instead of registering.
- **A stale rebind cannot consume its replacement's state.** After its wire call resolved, `rebind` only checked that the key still existed — but the key may since belong to a *different* record. It then mutated the dead record, ate the replacement's buffered notification and emitted `subscription-restored` for a subscription nobody holds. Every post-await guard now compares record identity.
- **A handler subscribed from inside a handler is called once.** `deliver` iterated the live handler set, and a `Set` iterator visits entries added while it runs — so the new handler received the same status twice, once from its own replay and once from the loop catching up. Fan-out now iterates a snapshot.
- **TCP/TLS sockets stay in binary mode.** `setEncoding('utf-8')` handed over a string Node's decoder had already "repaired": a malformed byte arrived as U+FFFD inside JSON that still parses, so corruption reached the caller as data and the strict validator never saw the bytes that caused it. Both transports now decode the bytes themselves.
- **Decoding no longer depends on the platform decoder at all.** Validated bytes are assembled by the library when `TextDecoder` is missing or when it fails a startup probe — and it is probed, because `ignoreBOM` is the third option React Native's polyfill accepts and ignores. Without it, a U+FEFF that happened to start a chunk was silently deleted, making output depend on where the network split the stream.

- **A status pushed in the same chunk as its subscribe response is no longer lost.** A server may answer `subscribe` and push the first change together; the transport frames and dispatches both lines synchronously, while the wire call's resolution only schedules the registry's continuation — so the notification reached `notify` before the record existed (first subscribe) or while it was still orphaned (rebind) and was dropped. The caller then sat on the subscribe's own status until the *next* change, which for a wallet is a missed transaction. Such a push is now held per key and delivered after the record binds, in wire order, and only if it came from the server that answered.
- **A delimiter flood no longer allocates in proportion to the delimiters.** `LineFramer` used `split('\n')`, which materializes an entry for every segment before any of them can be measured, so 8 MiB of newlines built an 8-million-element array (~180 MB RSS) despite the line cap. The framer now scans delimiter positions and slices only the lines it emits.
- **A line's legality no longer depends on where the transport split its reads.** `'abcde\r\n'` in one chunk was accepted while `'abcde\r'` + `'\n'` hit the cap, because the provisional CR counted as line content. A trailing CR is now excluded until the next chunk decides what it is.
- **A TCP/TLS candidate that fails to connect can no longer emit data.** `reject` only schedules, so the generation stayed current until the catch ran a microtask later — an injected socket (the case `TcpSocketLike` exists for) emitting `error` and then `data` in the same turn surfaced bytes from a connection whose `connect()` had already failed. The error path now retires the generation and destroys the socket before rejecting.
- **An undecodable WebSocket frame is terminal.** It emitted an `error` and left the socket open; `ElectrumClient` deliberately ignores a standalone transport error and waits for close, so every in-flight request hung to its timeout with no reconnect scheduled — and on Hermes (React Native), which has no `TextDecoder`, one binary frame was enough. The transport now tears the connection down and emits `error` + `close`, as it does for the line cap.
- **Binary frames decode across chunk boundaries.** Both transports decoded each frame/chunk independently, so a multi-byte character split across two of them (a server banner is free-form UTF-8) became replacement characters in both halves and corrupted the JSON line carrying it. Each connect attempt now owns a `Utf8Stream` that holds the trailing bytes of a half-received character until the chunk that finishes it. `TextDecoder`'s own `{ stream: true }` was tried first and on-device CI rejected it: React Native's polyfill accepts the flag and ignores it, decoding a split `€` as three replacement characters — so the tail is carried in our own code, and the platform decoder only ever sees whole characters.
- **A truncated binary stream cannot reorder itself around a text frame.** WebSocket permits mixing frame types; a binary frame ending mid-character left those bytes in the streaming decoder, so a later binary frame completed that character *after* text that arrived earlier on the wire — reordered content, with a newline potentially landing in the wrong line. A text frame now flushes the decoder, and a stream that was holding an incomplete character is terminated as undecodable.
- **Malformed UTF-8 ends the connection instead of reaching the application.** Both transports decoded non-fatally, so an invalid byte became U+FFFD and the surrounding JSON stayed syntactically valid — corruption inside a txid, an address or a script would have been delivered as data. Validity is now decided by the library's own scanner (`src/transport/utf8.ts`), which rejects bare continuation bytes, overlong forms, UTF-16 surrogates and code points past U+10FFFF, and a decode failure is terminal like any other unreadable frame. `TextDecoder`'s `fatal` option cannot be relied on: React Native's polyfill accepts it and returns replacement characters anyway.
- **An unreadable TCP chunk is terminal too.** A chunk of an unknown shape (an injected socket that ignores the encoding hint on a runtime without `TextDecoder`) emitted an `error` and was skipped, leaving the socket published and the framer's view of the stream one hole short. `ElectrumClient` ignores a standalone transport error, so in-flight requests hung to their timeouts with no reconnect scheduled — the same defect already fixed for WebSocket.

- **Subscriptions now bind to the server that actually answered.** The registry stored the *preferred* pick in the record; when the subscribe (or rebind) wire call failed over to another server via the retry pipeline, notifications from the real owner were silently dropped (`notify` compares sender ids) and the wire unsubscribe went to the wrong server — leaving a ghost subscription on the fallback (stale wallet state + a privacy leak). The internal pinned-call path now reports `servedBy` and records bind to it; if the serving client died mid-call the record lands orphaned and the rebind loop picks it up.
- **Clients whose resume() connect failed now re-enter auto-reconnect.** Their `disconnected` transition fires while the lifecycle is `resuming`, where the reconnect runner is gated; nothing re-armed the loop after the flip to `running`, so one failed connect during an RN foreground transition left that server dead until app restart. `runResume` now sweeps non-connected clients into `reconnect.schedule` after the lifecycle flips.
- **`WsTransport.close()` is bounded.** A dead or non-compliant peer that never completes the close handshake used to park `stop()`/`suspend()` forever; close now mirrors TcpTransport's 500 ms backstop and force-terminates where the runtime supports it.
- **`prepack` builds before publish** — `dist/` is git-ignored and nothing previously guaranteed a fresh build, so a manual `npm publish` could ship stale artifacts that no CI run ever tested.
- Fulcrum answers a batch over its item cap (345 items at v1.11 defaults, measured empirically) with a single `{error, id: null}` object — `"Batch limit exceeded"`, code 4 — instead of a response array. That reply no longer stalls every item of the batch until `requestTimeoutMs`: the client tracks open wire batches in send order and maps the id-less error onto the oldest one (batches are answered in order on a connection), and the classifier treats `batch limit exceeded` as rate-limit, so all items re-route to another server immediately. A 400-item batch against live Fulcrum with an ElectrumX fallback resolves in ~1s where it previously sat out the full timeout. ElectrumX 1.18 and electrs 0.11 accept 1000+ item batches (overload there surfaces per-item or by disconnect), so the shape is Fulcrum-specific today but JSON-RPC-2.0-legal for any server.
- `WsTransport` no longer constructs a `TextDecoder` in its field initializer — on stock React Native Hermes (no global `TextDecoder`) even `new WsTransport(...)` threw, and ws/wss is the primary RN transport. The decoder is now created lazily on the first binary frame; `Buffer` frames decode without it, and an undecodable frame surfaces as a transport `error` event instead of being dropped silently (a dropped frame otherwise shows up as a hung request).
- `TcpTransport.connect()` no longer constructs a `TextDecoder` eagerly. Stock React Native Hermes has no global `TextDecoder`, so every TCP/TLS connect threw `ReferenceError` on RN unless the app happened to polyfill it. The decoder now materializes only on the defensive path (a socket shim that ignores `setEncoding` and emits raw `Uint8Array`s); without a decoder there, the chunk surfaces as a transport `error` event instead of crashing. Found by reviewing what the on-device test harness polyfills versus what consumers actually get.
- A failed subscription rebind no longer strands the subscription until the next client state transition. Previously, if the wire `subscribe` issued by `restoreOrphans` failed (e.g. timed out on a freshly reconnected but not-yet-usable link), the record stayed orphaned silently — no retry, no event — until another disconnect/connect cycle. `rebindOnce` now retries with backoff (1s doubling, 10s cap) for as long as some client is connected. Found by running the integration suite on-device: the Android emulator's NAT reliably produces an established-but-dead first connection after a toxiproxy re-enable, which is exactly the shape of a mobile-network reconnect.
- Classifier no longer claims `"excessive resource usage; bye!"` is a Fulcrum string — that wording is from aiorpcx (ElectrumX's RPC framework) and never appears in Fulcrum payloads. Fulcrum's actual rate-limit message (`"Subscription limit reached"` from `impl_generic_subscribe`) is now matched explicitly. The generic substring set picks up the same string when `serverSoftware` is unknown, so ban detection works without an explicit `server.version` handshake.
